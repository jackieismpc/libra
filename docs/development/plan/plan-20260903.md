# Merge 能力对齐 Git 计划（2026-09-03）

## 文档职责

本文解决 `libra merge` 与 `git merge` 在算法层与内容层的能力差距，目标是：`libra merge` 主路径能力（rename 检测、多 merge-base recursive 合并、D/F 冲突、增量树合并、merge driver、冲突精化、octopus、策略框架、mergetool、签名与消息面）与 Git 对齐；完成后与 Git 的剩余差距**仅为**（a）永久非目标的 subtree / submodule / gitlink（ADR-MG-01），以及（b）「非目标与延后项」中逐条登记的有意差异（DEFER-01 ~ DEFER-14）。

本文只规划任务，不宣称实现完成。落地时每个任务都必须先刷新源码锚点，再按任务卡验收。

### 适用范围

- `libra merge` 命令全表面：`src/command/merge.rs`、`src/internal/merge_base.rs`、`src/command/rename_detect.rs`（复用）、`src/command/rerere.rs`、`src/internal/pseudo_ref.rs`、新增 `mergetool` 命令。
- 受影响的状态面：`<worktree gitdir>/merge-state.json`、pseudo-ref 投影（`MERGE_HEAD`/`ORIG_HEAD`/`AUTO_MERGE`）、冲突 index stage 1/2/3。
- 复用方同步：`cherry-pick` / `revert`（已复用 merge 内容合并）、`rebase`（收敛到统一三路引擎）。
- 测试：`tests/command/` 各模块（统一编译进 `command_test` 单 binary，见事实基线「测试」行）、`tests/compat/*`；文档：`docs/commands/merge*.md` EN+zh、`docs/development/commands/merge.md`、`COMPATIBILITY.md`、`docs/error-codes.md`、`tests/INDEX.md`。

### 非目标

- **subtree 合并（`-s subtree` / `-X subtree`）、submodule/gitlink 合并：永久非目标**（产品定位 monorepo 客户端，见 ADR-MG-01）。gitlink 条目由「静默跳过」改为「裁决触及即 fail-closed」，仍不实现合并。
- `merge-tree --write-tree`（独立命令，不是 `git merge` 表面）——DEFER-01。
- `-X diff-algorithm=<patience|histogram|minimal>`（diffy 内核单一算法）——DEFER-02。
- mergetool 全量 25+ 外部工具描述文件——DEFER-03。
- 合并签名 tag 的 `mergetag` header 嵌入与 throwaway tag 强制 no-ff——DEFER-04。
- `merge.rs` 模块拆分（预计超 5000 行后的 `src/internal/merge/` 归位）——DEFER-05。
- 目录 rename 推断与 rename/rename 叠加的其余角落案例（MG-07 AC4 采样组合之外）——DEFER-07。
- cherry-pick 的 rename 接入；外部 `git-merge-<name>` 策略命令发现——DEFER-06。
- `merge.<name>.recursive` 低层 driver 的递归调用语义——DEFER-08。
- `-X find-renames[=<score>]` / `rename-threshold` flag 别名——DEFER-09。
- 显式 `-s octopus` 策略名——DEFER-10。
- `mergetool.keepBackup` 之外的 `mergetool.*` 配置面——DEFER-11。
- 外部 GPG keyring / SSH 签名（merge 签名仅 vault，与 commit 现状一致）——DEFER-12。
- merge 默认打开编辑器（保持 Libra「不自动开编辑器」现状；Git 默认 `--edit`）——DEFER-13。
- `merge.suppressDest` 等 fmt_merge_msg 衍生配置——DEFER-14。
- `merge-file` 的 `-L`/`--union`/`--marker-size` 补齐（独立命令表面，不在本计划）。

### 成功定义

- 日常重构场景（一侧 rename + 对侧修改）自动合并成功，不再退化为 modify/delete + add 两条独立记录；criss-cross 历史经 recursive 虚拟祖先合并，结果与 Git 一致。
- D/F 冲突、rename/rename、rename/delete、rename/add 冲突被显式检测并按 Git 语义呈现（stage 1/2/3 + 人读提示）。
- merge driver（gitattributes `merge` 属性、内建 text/binary/union、外部 driver）、`-X ignore-space-*`、`merge.conflictStyle=zdiff3`、冲突精化与 Git 行为一致。
- octopus 多分支合并、`-s ort/recursive/resolve`、多 `-s` 回退选择、`mergetool`、`-S/--gpg-sign`、`--signoff`、`--quit`、`--edit` 可用。
- 大仓库下 merge base 计算与树合并不再全量扫描（复杂度界写入「性能与容量摘要」并有 benchmark 证据）。
- `COMPATIBILITY.md` merge 行更新为「主路径与 Git 对齐；剩余差异 = 永久非目标（subtree/submodule/gitlink）+ DEFER-01~14 登记项」——**不**宣称「仅三项例外」，DEFER 项在兼容矩阵中逐条可见。
- 全量收口门全绿；Codex review 最终 PASS。

## 已决议设计决策

实现时若需偏离本节，必须先修改计划并说明原因，不得在代码中静默改语义。

### ADR-MG-01: subtree/submodule/gitlink 永久非目标；gitlink「裁决触及才 fail-closed」

- **Status:** Accepted
- **Context:** Libra 定位 monorepo 客户端，submodule/subtree 不是目标工作流；当前 merge 与 rebase 的 tree 拍平（`merge.rs:2666`、`rebase.rs:3842`）静默丢弃 gitlink，参与合并时会产生错误结果。但「任一输入 tree 含 gitlink 即拒绝」又会误伤大量无害场景（gitlink 子树三方一致时没有任何合并决策要做），且与剪枝优化（MG-03）冲突。
- **Decision:** 不实现 subtree 合并与 gitlink 合并。语义分两档：① 三路合并**裁决触及**的 gitlink 条目（任一侧与 base 不一致、或需要写入合并结果的路径）→ fail-closed，报可操作错误（路径 + 「Libra 不支持 submodule」）；② 三树一致（含被剪枝）的 gitlink 子树 → 原样 pass-through（内容逐字节来自输入，不产生合并决策，不构成错误结果）。merge/rebase/cherry-pick 共用同一校验 helper。
- **Alternatives considered:** 维持静默过滤（正确性风险，拒绝）；任一输入含 gitlink 即全拒（误伤无害场景、与剪枝冲突，拒绝）；实现 gitlink 可达性合并（超出产品定位，拒绝）。
- **Consequences:** 纯 Libra 工作流无影响；外部含 submodule 仓库的合并在「submodule 指针有分歧」时被拒绝而非出错结果；pass-through 语义是未来若支持 gitlink 时的兼容路径。
- **Revisit when:** 产品定位变化、决定支持 submodule 时。

### ADR-MG-02: 内容合并继续以 diffy 为行级内核，高级语义在其上自建

- **Status:** Accepted
- **Context:** 冲突精化、whitespace-ignore、union、driver 分派在 Git 由 xdiff/ll-merge 承载；Libra 已用 diffy 0.4.2 且有大量既有测试钉住标记格式。
- **Decision:** 保留 diffy 作为行级 diff3 内核；merge driver 分派、renormalize、whitespace 归一化、冲突精化（对 diffy 输出的冲突块再跑 diff 缩小）作为 Libra 自建层置于内核之上。`-X diff-algorithm=*` 因 diffy 单一算法而 DEFER。
- **Alternatives considered:** 移植/绑定 xdiff（工作量大、收益不覆盖成本，拒绝）；换 similar crate（同样无 zealous refine，拒绝）。
- **Consequences:** 精化后冲突块与 Git 字节级一致不作硬性承诺，判据为「语义一致（同真冲突、同自动合并结果）+ 既有格式测试不回归」。
- **Revisit when:** diffy 停止维护或出现必须字节级对齐的需求。

### ADR-MG-03: rename 检测按侧进行（base→ours、base→theirs 两轮），复用 rename_detect

- **Status:** Accepted
- **Context:** Git ort 的 rename 是 per-side 检测后处理路径级冲突（`merge-ort.c:3429`）；Libra 现有 `rename_detect::match_pairs` 接受删除/新增快照配对，语义吻合。
- **Decision:** merge 对 base→ours 与 base→theirs 各跑一次 `rename_detect::match_pairs`；三路匹配键由「同一路径三元组」扩展为「经 rename 表重定向的三元组」；rename 冲突类型按 Git 分类落地。目录级 rename 推断作为独立后续卡（MG-07）。
- **Alternatives considered:** 引入 diffcore-rename 式全量相似度矩阵新实现（重复造轮子，拒绝）。
- **Consequences:** `merge_tree_items()`/`resolve_three_way()` 需要重构以支持路径重定向；rename 检测的预算控制（`RenameDetectConfig`）沿用 status/diff 的默认值并允许 `merge.renameLimit` 类配置。
- **Revisit when:** rename 检测成为 merge 热路径性能瓶颈（届时评估 cached_pairs 类缓存）。

### ADR-MG-04: 保持 Libra 全内存合并 + sidecar 状态架构，不引入 Git 的 index 中间态

- **Status:** Accepted
- **Context:** Git ort 先全内存合并再 `merge_switch_to_result()` 一次性写回；Libra 现有架构同构（内存决策 → 写 index stage/工作区/sidecar）。
- **Decision:** 新能力（recursive 虚拟祖先、octopus、rename）全部在该架构内实现；虚拟祖先只作为内存中的合成 tree/commit，不落对象库之外的中间态；recursive 合并产生的虚拟 base 不写入 `merge-state.json`（崩溃恢复时由 target/base 重算，与 `--restart` 现有语义一致）。
- **Alternatives considered:** 移植 Git 的 AUTO_MERGE + unpack_trees 体系（与 Libra 存储模型不匹配，拒绝；AUTO_MERGE 的**投影**由 MG-21 在本架构内实现，仅 merge 进行中可观察）。
- **Consequences:** recursive 虚拟祖先的 tree/合成 commit 对象作为一次性 loose object 写入对象库；因不写入 `merge-state.json`，它们不被 `merge_state_gc_oids`（`src/command/merge.rs:367` 起的语义 OID 收集）引用，`maintenance gc` 可将其回收——这是预期行为而非缺陷：中断恢复不依赖虚拟对象存活，恢复路径仅为 `--restart` 由 target/base 重算（`--continue` 不做虚拟祖先重算，其只加载既有 state/index 收尾，MG-02 故障注入用例验证「GC 回收 → `--restart` 重算恢复」）。
- **Revisit when:** 出现嵌套 depth 过大导致的性能或栈深度问题。

### ADR-MG-05: octopus 只做树级无冲突合并，与 git-merge-octopus.sh 语义一致

- **Status:** Accepted
- **Context:** Git 的 octopus 策略在非最后一个 head 出现需手工解决的冲突时整体失败（"Should not be doing an octopus"）。
- **Decision:** Libra octopus 同样只接受全自动可合并情形：逐 head 三方合并，任一 head 产生内容级冲突即整体拒绝（不留下半成品状态）；`--no-ff` 语义与多父提交（parents = HEAD + 全部 remote heads）与 Git 一致。
- **Alternatives considered:** 允许 octopus 冲突进入人工解决（Git 自身也不支持，拒绝）。
- **Consequences:** 需要 `merge_bases` 的 octopus 变体（`get_octopus_merge_bases` 等价物）；`MergeArgs` 分支参数从 `Option<String>` 改为 `Vec<String>`，单分支行为完全不变。
- **Revisit when:** N/A（与 Git 对齐即终态）。

### ADR-MG-06: pseudo-ref 在共享对象解析 seam 中以「调用方 opt-in」接入

- **Status:** Accepted
- **Context:** `util::resolve_object_spec_typed`（`src/utils/util.rs:2124`）被 rev-parse、cat-file、update-ref 等多个调用方共享；update-ref 的 `<oldvalue>` CAS 操作数不做 commit 类型检查（`update_ref.rs:452` `resolve_old_value`，其 doc comment 明示 "deliberately no commit type check"，resolver 调用在 `:461`；对比 `:389` 起的 `resolve_new_value` 在 `:421` 有 commit 类型检查）。若在 seam 中无条件启用 pseudo-ref 解析，update-ref 会意外接受 AUTO_MERGE 的 tree OID，改变既有拒绝语义。
- **Decision:** seam 的 pseudo-ref 解析为**调用方 opt-in**（显式能力参数/开关）：只有 rev-parse、cat-file、diff 三个本计划声明的表面启用 AUTO_MERGE 解析；未 opt-in 的调用方（update-ref 及其余全部现有调用方）行为零变化，对 pseudo-ref 名称继续保持拒绝。
- **Alternatives considered:** seam 无条件启用（update-ref 语义被破坏，拒绝）；在三个表面各自实现 pseudo-ref 解析（违反 GC-02 单一事实源，拒绝）。
- **Consequences:** 既有六个 pseudo-ref 的「rev-parse 不可解析」契约中，AUTO_MERGE 成为**唯一例外**（仅 merge 进行中、仅 opt-in 表面可解析）；compat 测试必须拆 resolve/reject 两组并把名称提取从 `_HEAD` 启发式改为显式集合。
- **Revisit when:** 出现新的需要消费 pseudo-ref 的表面（逐一评审 opt-in）。

### 故障恢复矩阵

| 故障点 | 可接受残留 | 恢复动作 | 禁止结果 |
|---|---|---|---|
| recursive 虚拟祖先写入对象库后、合并完成前崩溃 | 虚拟 tree/commit 成为 loose object | 由 merge state 的 target/base 在 `--restart`/`gc` 时重算或回收（一次性对象，ADR-MG-04） | gc 回收后 `--restart` 无法重算恢复；半成品 merge state 被当作干净 |
| 外部 driver 执行中信号中断 | 0700 临时目录残留 | 下次 merge 启动时清理或权限隔离 | 残留文件含敏感内容且权限宽松；index 半成品 |
| octopus 中途某 head 冲突 | 无（原子拒绝） | 整体失败，用户改用逐分支 merge | 部分 head 已落 index/worktree |
| AUTO_MERGE 投影写入后崩溃 | 悬空 pseudo-ref（结果树 OID 在 MergeState 中，GC root 覆盖） | 状态清理路径（`--continue/--abort/--quit`）幂等删除 | GC 误删指向 tree；ref 永久残留；clean merge 留下常驻投影 |
| mergetool 工具非零退出 | `.orig` 备份（keepBackup 语义） | 路径保持未解决，用户重跑 | 未解决路径被静默 stage |
